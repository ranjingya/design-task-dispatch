# design-task-dispatch

美工需求识别与任务分配服务，使用 Flask，单进程运行。

## 当前能力

- 接收 `POST /webhook/task`，校验共享密钥和记录 ID，在单个后台线程执行评级。
- 读取需求及工作类型单选选项；规则表全量分页读取后保存为每日本地快照。
- 支持 PNG、JPEG、WebP 图片、Excel、Word 与 PDF 附件，以及「需求文档链接」中的飞书文档、知识库、电子表格和多维表。文字保留来源、段落、工作表坐标或页码，图片进入统一的多轮识别材料池。
- 模型返回固定 JSON，程序校验规则 ID、部门范围、类型名称及等级，再回写工作类型、分类等级、匹配结果和任务负载分。
- 信息不足、规则冲突或附件无法完整读取时，匹配结果展示候选规则、可能匹配的依据、未确定原因及待补充信息；工作类型、分类等级和任务负载分清空，避免保留过期评级。
- 模型网络异常、限流和部分服务端错误最多尝试三次；非法输出不会写入工作类型。失败提示写入匹配结果，详细异常留在日志。
- 对处理中及最近五分钟成功完成的记录去重；失败记录可重新投递。
- 字段映射接收任务时读取，提示词调用模型前读取；业务数据及结果保存在飞书。

人员推荐在评级后执行，组长确认最终负责人。ZIP、RAR、7Z 素材压缩包跳过，不单独导致待确认；XLS 提取文字后提示转为 XLSX 核对图片。PPT、音视频、GIF 等未支持附件进入待确认；外部网站和网盘链接不读取。

## 规则快照

每天第一条需求触发规则刷新，当天后续需求使用本地快照，无需求时不请求规则表。自然日按服务所在时区计算，Docker 为 Asia/Shanghai。每次调用模型仍发送本次匹配所需的规则内容。

本地默认保存到 `.cache/rules.json`，可通过 `RULES_CACHE_PATH` 指定。Docker 使用 `rules-cache` 持久化卷中的 `/app/cache/rules.json`，容器重建后保留。快照包含来源 Base、规则表 ID、日期和全部原始规则，来源不一致或文件损坏会重新加载。刷新校验成功后原子替换文件。

刷新失败时使用最后可用快照并记录警告，下一条需求重试；没有可用快照则处理失败。当天修改飞书规则，次日首次需求生效；需立即生效时删除规则快照，下一条需求会重新读取。提示词及字段映射仍按每次任务读取。

## 评级配置

在 `.env` 配置同一 Base 下的 `FEISHU_RULES_TABLE_ID`，以及 `DEEPSEEK_BASE_URL`、`DEEPSEEK_API_KEY`、`DEEPSEEK_MODEL`。接口地址可包含 `/v1`，程序追加 `/chat/completions`。模型使用思考模式进行规则判断，输出上限默认 16384 tokens（包含模型推理），可通过 `AI_MAX_OUTPUT_TOKENS` 设置为 1024～32768。默认超时 90 秒，可通过 `AI_TIMEOUT_SECONDS` 调整；`AI_MAX_ATTEMPTS` 为总尝试次数，范围 1～3。

`config/fields.json` 中 `work_type`、`level` 对应「工作类型」「分类等级」单选字段，`department` 对应「部门」单选字段，`platform` 对应「平台」文本字段，`load_score` 对应「任务负载分」数字字段，`rule_explanation` 对应「匹配结果」文本字段，`attachments` 对应附件字段。`config/rule_fields.json` 映射规则表的类型、内容、部门、默认等级、调整说明、分配方式和人员负载分数，每次任务重新读取。规则表与需求表位于同一 Base。

首次处理时，程序将创建人复制到空白的「需求人」人员字段；已有值保持不变，重跑保留手动修改，后续评级失败也保留已初始化的需求人。创建人字段只读，用于需求人初始化和部门归属。

程序读取 `config/fields.json` 中 `creator` 对应的「创建人」字段，通过应用身份查询通讯录，从直属部门逐级向上匹配规则表「适用部门」。唯一确定部门后回写「部门」，仅向模型发送该部门适用的规则。「需求人」、原部门值和平台不参与创建人部门归属判断。创建人缺失、通讯录不可读、路径无匹配或多部门冲突时，匹配结果写「创建人员部门未知」，清空自动分类、分数和推荐人员，跳过材料读取及 AI 调用。已人工安排或结束的任务仍保留原结果。通讯录成功结果在进程内缓存 24 小时，重启服务可刷新；无权限响应不缓存。

应用需具备人员组织架构、部门基础信息和部门组织架构读取权限，通讯录可见范围覆盖创建人及上级部门。规则「适用部门」支持多选标签与分隔文本，类型和等级支持单选标签。规则名称可以相同，规则 ID 必须唯一；回写文本展示匹配类型与具体工作内容，规则 ID 保存在服务日志中。

在适用部门范围内，标题或需求说明明确命中「包含的工作」关键词时优先匹配；更具体的工作描述优先于宽泛相关项。未提供套版等细节时使用规则默认等级，明确符合调整条件才升降档。仅在实际多规则歧义、信息过少或内容冲突时返回候选，不猜测需求未提到的使用场景。

`prompts/classify.md` 保存判断要求及 JSON 输出协议。输出包括 `matched`、`department`、`rule_id`、`level`、`work_type`、`reason`、`candidates`、`unmatched_reason`、`missing_information`。程序只校验结构和引用一致性，具体分档准确性需要业务样本验证。

本地材料池默认最多 32 张原始图片，单张或切片 10 MiB，预览及清晰分段总计 20 MiB，可通过 `MAX_IMAGES`、`MAX_IMAGE_BYTES`、`MAX_TOTAL_IMAGE_BYTES` 调整；编码后的完整模型请求限制为 45 MiB。参与识别的附件不支持、过大或下载失败时，向模型明确传入材料缺口；只允许输出候选，禁止基于部分材料给出确定评级。

模型接口参考：[JSON 输出](https://api-docs.deepseek.com/guides/json_mode/)、[图片输入](https://api-docs.deepseek.com/guides/vision/)。

## 人员负荷统计

准确匹配后，程序根据模型返回并通过校验的规则 ID 读取该条「人员负载分数」，将数字与评级结果一次回写需求表的「任务负载分」。同名工作类型按具体规则区分，分数不由模型生成，也不按分类等级或数量换算。规则分数缺失、为负或不是有效数字时，保留分类结果，负载分留空并在匹配结果说明；0 是有效分数。

「任务负载分」可在日常视图隐藏，由程序维护。它保存本次处理采用的规则分数，重新处理时更新。规则快照按自然日刷新。

成员负荷表按人员自动汇总全部日期的任务，排除「是否取消」及已有「实际完成时间」的任务。标题中的测试标记仅用于人工识别，任务照常参与负载统计与同分轮换：

- 未完成任务：组长已确认，最终负责人为该成员。
- 待确认推荐：组长尚未确认，系统推荐人为该成员。
- 总负载分：未完成负载分与待确认负载分之和。

负载分仅汇总有效的非负分数，缺分或负数任务暂不计分；没有有效计分任务时显示 0。任务数按实际记录统计。补充分数后，负荷表自动计入，程序在下次推荐时使用最新分数。程序每次从完整需求记录实时计算同口径负载，排除当前需求已有预占。

## 本地运行

使用 Python 3.14 与 uv：

```bash
uv sync
cp .env.example .env
```

已有 `.env` 时直接补充所缺参数，保留应用凭证。评级配置缺失时，任务会失败并写入匹配结果。`WEBHOOK_TOKEN` 填写随机密钥，并在飞书自动化请求头中填写相同值。

```bash
uv run flask --app app.main:create_app run --host 127.0.0.1 --port 8000
uv run pytest
# 可选：真实模型业务回归，产生 API 调用但不写入飞书
LIVE_AI_TESTS=1 uv run pytest tests/test_live_rating.py -q
```

开发时关闭自动重载，保证内存去重由单个进程维护。

## Docker 部署与外部配置

GitHub Actions 在推送 `v*` 标签或手动触发时构建根目录 Dockerfile，将镜像推送到 GHCR，再通过 SCP 和 SSH 部署。

仓库配置变量 `DEPLOY_DIR` 为本项目独立部署目录；配置 secrets：`SSH_HOST`、`SSH_PORT`、`SSH_USER`、`SSH_PRIVATE_KEY`、`SSH_PRIVATE_KEY_PASSPHRASE`。首次部署前在服务器部署目录准备 `.env`，并确保已有 Traefik 外部网络 `traefik-network`。

镜像地址为 `ghcr.io/ranjingya/design-task-dispatch:latest`，工作流使用仓库所有者作为 GHCR 命名空间；仓库应位于 `ranjingya` 名下，若使用其他组织则同步修改 Compose 镜像前缀。

自动部署仅复制 Compose 文件。首次部署从镜像初始化 `config/fields.json` 和 `prompts/classify.md`，后续部署保留服务器已有配置。上线评级功能前，需同步 `config/fields.json`、`config/rule_fields.json` 和 `prompts/classify.md` 到服务器部署目录，并补齐规则表与模型环境变量。完成首次部署后，可手动执行：

```bash
docker compose pull design-task-dispatch
docker compose up -d design-task-dispatch
docker compose logs -f design-task-dispatch
```

部署目录下的 `./config` 挂载到 `/app/config`，`./prompts` 挂载到 `/app/prompts`，均为容器内只读。字段配置在宿主机的 `config/fields.json`、`config/rule_fields.json` 中维护。提示词在宿主机 `prompts/classify.md` 修改，下次模型调用生效，无需重建镜像。

修改宿主机 `config/fields.json` 后，下一个新任务读取最新映射；处理中任务继续使用接收时的快照。JSON 无效时新请求返回 503，修复文件后重试即可，无需重建镜像。环境变量修改后执行 `docker compose up -d --force-recreate`。

镜像使用 Gunicorn，固定一个进程、四个请求线程和一个后台处理线程。Traefik 通过 `traefik-network` 访问容器的 8000 端口，使用 `websecure` 入口和 `myresolver` 证书解析器提供 HTTPS：

`https://design-dispatch.kktree.cn/webhook/task`

域名需解析到部署服务器；Traefik 的入口、证书解析器及外部网络沿用服务器已有配置。

## 飞书自动化

触发条件：需求任务表添加新记录且任务名称非空。执行动作：发送 HTTP POST。

- 请求头：`Content-Type: application/json`
- 请求头：`X-Webhook-Token: 与 .env 中 WEBHOOK_TOKEN 相同的值`
- 请求体：`{"record_id":"第 1 步新增记录的记录 ID 变量"}`

成功接收返回 202，重复请求返回 200；这些回执只确认请求接收情况。后台评级结果写回多维表，错误记录在服务日志中，不输出需求正文或应用凭证。

`GET /health` 仅检查 HTTP 服务存活。

## 运行边界

任务及去重记录保存在内存，重启后需重新触发未完成任务。后台失败通过日志定位，修复后重新投递。最多同时接收 100 个等待或执行中的任务，超出返回 503。当前只运行一个实例，跨进程、跨实例不共享去重状态。

飞书应用需要需求表的读取及编辑权限、规则表读取权限，以及附件素材下载权限。用户身份可访问表格与自建应用身份可访问表格是两套授权。

## 人员推荐

`config/recommendation.json` 与字段映射放在同一目录，随现有 config 挂载到容器外。每条需求重新读取，包含人员昵称与用户 ID 映射、规则记录 ID 到归属查询方式的映射、轮换顺序、商品字段及货号识别规则、店铺主次负责人和别名。成员名单必须与成员负荷表一致。

- 轮流：全体成员中总负载最低优先，同分按配置顺序轮换。
- 固定人员：解析规则括号内名单，在指定人员中负载优先、同分轮换。
- 人工分配：系统推荐人留空，推荐结果展示成员负载参考，由组长结合文档中的创意方向及平台要求安排。
- 找对应人员：按具体规则 ID 查询商品或店铺归属；未配置路径转人工。

商品归属读取数据包分配表的完整分页记录，提取完整货号，区分单款与拼款；拼款要求完整货号组合，并检查配置中的平台限制。多个匹配记录认领人为同一人时可沿用；人员不同、认领为空、货号不全或平台无法对应时转人工。普通商品归属路径中，明确为老款且未查到货号时进入全员负载比较。花菜等排除人员、未配置人员直接转人工。来源读取失败属于推荐失败，不作为无归属兜底。

数据包创意图通过 `product_platform_rules` 配置平台别名和动作：京东／JD 沿用认领人员；拼多多／PDD 排除原认领人员，在其余成员中负载优先、同分轮换。仅依据提报的平台选择策略；平台不明、多个平台或归属不明时转人工。

店铺先按部门及平台筛选，再将需求字段中的标准名称／别名归一化匹配。平台简称、全半角、大小写、空格和标点按配置统一；简称需在当前部门和平台内唯一。匹配成功后将主负责人及所有副负责人写入系统推荐人，主负责人在前，副负责人按 `backup` 配置顺序排列，重复人员仅保留一次；推荐说明按相同顺序展示各人负载。组长确认前，主副负责人各预占整条任务分数；确认后按最终负责人统计，每人计入整条任务分数。

店铺目录保存在 `config/recommendation.json` 的 `shops`：每项包含稳定的 `id`、标准名称 `name`、`department`、`platform`、`aliases`、`primary`、`backup`。`shop_platforms` 保存标准平台到简称的映射，`shop_ai_fallback` 控制 AI 消歧。当前服饰店的已确认别名包括「拼多多服饰店」「pdd服饰店」。新增别名修改对应店铺的 `aliases`，新增店铺使用独立 ID；AI 判断结果用于当前任务，别名由人工维护。

程序无法唯一匹配时，AI 使用候选店铺、需求字段及已读取文档的来源名称和正文进行消歧。模型必须返回候选目录中的店铺 ID，以及可在本次材料中核验的原文引用；负责人由程序读取配置。文档中的店名由 AI 结合上下文判断是否为本次交付对象，区分参考店铺与目标店铺。平台冲突、材料缺失、模型故障或证据不足时转人工确认，并在推荐结果中列出候选店铺和具体原因。

店铺识别提示词为 `prompts/identify_shop.md`，与分类提示词放在同一目录。部署店铺识别功能时，同步 `config/recommendation.json` 和该提示词；两者下次任务读取生效，Python 逻辑随镜像发布。

归属推荐保留负责关系。负载比较模式按候选范围内每个人已计入的有效分数选择，历史任务缺分不影响人员参与推荐。推荐结果展示各人已计分负载，有缺分任务时补充「N 条待计分」提示；服务日志记录暂未计分的任务来源。没有最终负责人或系统推荐人的任务不计入任何人员的负载。当前需求未准确匹配规则或规则分数无效时，由组长人工分配。已取消、完成、指定最终负责人或组长确认的记录保留原结果，回写前再次读取检查。

评级与推荐字段一次回写；推荐读取失败时保留评级结果、清空系统推荐人，并在推荐结果提示重试。匹配结果负责解释规则，推荐结果负责解释人员选择。匹配结果展示匹配状态和具体工作内容，等级调整时补充原因；待确认时展示候选及缺失信息。推荐结果固定四行：推荐方式、规则或原因、相关人员当前负载、本任务分数。规则与归属记录 ID 保存在服务日志中。

轮换位置保存在规则缓存同目录的 `rotation.json`，按候选人员集合区分轮转池，飞书回写成功后原子保存。重跑同一任务时，原推荐人仍处于最低负载候选中则保留。测试记录不计入正式负载、不推进轮换。服务仍需单实例运行；飞书回写与本地轮换文件不是跨系统事务，极端中断可能让下一次同分轮换重复。回写前检查与飞书编辑之间也存在短暂竞争窗口。

多维表资源参数统一放在 `.env`：

- `FEISHU_BASE_TOKEN`、`FEISHU_TABLE_ID`：需求任务表。
- `FEISHU_RULES_TABLE_ID`：同一 Base 下的规则表。
- `FEISHU_MEMBERS_TABLE_ID`：同一 Base 下的成员负荷表。
- `FEISHU_PRODUCT_BASE_TOKEN`、`FEISHU_PRODUCT_TABLE_ID`：商品数据包分配表。

`.env` 使用简单键值，保存凭证、Base Token、表 ID、模型接口、超时重试及路径等运行参数，`.env.example` 提供模板。`config/recommendation.json` 的 `members` 保存昵称到用户 ID 的映射，`ownership_routes` 保存规则记录 ID 到 `product`、`shop` 或 `product_platform` 的映射；字段映射、名单及分配规则也在容器外 JSON 中维护，每次任务重新读取。修改 `.env` 后重建容器以加载新值。

应用需具备成员负荷表和跨 Base 数据包分配表读取权限。部署时同步 `.env`、 `config/recommendation.json` 和 `config/fields.json`；Compose 的现有目录挂载与缓存卷即可使用。

## 需求文档读取

`config/fields.json` 的 `document_link` 对应「需求文档链接」。该字段选填，支持允许域名下的 `/docx/`、`/wiki/`、`/sheets/`、`/base/` 链接，也支持多行链接文字。Wiki 先解析为实际资源类型。正文中的普通超链接只作为文字，不自动追踪。

- 飞书文档读取正文、表格、内嵌图片、附件、电子表格、多维表和画板预览；智能纪要读取其文档正文，音视频与交互控件不参与识别。未支持的内容块明确记录材料缺口。
- 飞书电子表格通过官方接口导出完整 XLSX，查询参数中的当前工作表不会限制读取范围。
- 飞书多维表按 `table`、`view`、`record` 定位读取；指定记录时仅读取该记录，否则读取指定视图或数据表的记录。多个数据表必须提供 `table` 参数，关联记录不继续展开。附件使用原始表、记录及字段权限下载。
- Word DOCX 读取正文、表格中的文字、页眉页脚、批注和内嵌图片；嵌入文件、图表等未能完整读取的内容标记材料缺口。旧版 DOC 使用 LibreOffice Writer 转成 PDF 后读取文字与页面图片；Docker 镜像包含转换器和中文字体，本地运行须安装 `soffice` 或配置 `word_converter` 路径。

应用须具有目标资料的阅读权限及相应文档、知识库、画板、电子表格或多维表 API 权限；在线电子表格还须具有导出权限。访问失败、资料不可见与链接格式错误分别提示，单份资料失败不会丢弃其他已读取材料。

`config/materials.json` 每次任务加载，随 config 目录挂载到容器外，配置文件大小、页数、工作表数、文本量、图片缩放、导出等待和域名范围。默认最多 10 个文档与图片文件，单文件 64 MiB、合计 128 MiB；Word/Excel 解压总量 256 MiB、20 张可见工作表、10 万个单元格；PDF 20 页；文本总量 6 万字符。图片限额通过现有 `MAX_IMAGES` 等配置控制，文档内图片与普通附件共享限额。

XLSX 读取可见工作表的缓存单元格值、批注、合并范围和锚定图片；不执行宏、公式或外部链接，隐藏页按配置跳过。缺失公式缓存、图表、特殊单元格图片或嵌入对象会提示材料缺口。PDF 逐页提取文字并渲染页面，扫描页直接交给视觉模型。加密、损坏、超限或权限不足均明确进入待确认，不声称完整读取。

上线时同步 `config/materials.json`、`config/fields.json` 和 `prompts/classify.md`，环境变量保持服务器路径。所需依赖随镜像安装。

## 图片总览与按需补图

图片先在程序内按工作表或来源分组，生成带 IMG 编号的缩略图总览，默认每张最多 6 个缩略图。来源、列标题、附近单元格说明通过图片目录提供。总览用于识别图片用途；模型按真实编号点选原图或尚未阅读的总览。原图长截图按顺序切成重叠分段，避免缩小后丢失说明文字。

`config/materials.json` 的 `visual_review` 配置在每条需求开始读取材料时加载：`max_rounds=3`、`first_round_images=5`、`next_round_images=10`。首轮最多 5 张总览，后两轮各最多补 10 张图片消息，累计最多 25 张新增图片消息；每张总览、原图或长图分段分别计数。此前发送的图片与回复保留在后续请求的上下文中，重试属于同一轮。目录编号稳定，不重复追加已发送图片。

首轮优先覆盖说明类来源，再轮转不同工作表。全部总览必须检查；明确的流程说明、修改标注、纯图片工作表、扫描页，以及正文要求看图的材料必须读取清晰原图。关键词在外部配置的 `instruction_keywords`、`image_reference_keywords`、`business_keywords` 维护。这些基于文字的识别规则提供覆盖检查，图片内容理解仍由模型完成。

模型返回 `action=request_images` 时给出带编号和原因的 `requests`；返回 `action=final` 时附完整评级字段。程序校验编号、保留待发送队列，禁止因提前输出最终结果而跳过必读材料。达到轮次上限仍未覆盖，或反复请求已读图片而缺少结论时，结果转待确认。仅在总览中阅读、没有放大的普通商品素材不构成材料缺口；实际下载、解析失败与超限仍明确提示。日志记录每轮新增图片、累计发送数及模型和评级耗时。

`prompts/select_images.md` 用于材料覆盖未完成时的选图阶段，仅提供需求、目录和图片；覆盖完成后使用 `prompts/classify.md` 并发送业务规则进行评级。两个提示词放在同一容器外目录。

### 飞书请求重试与手动重跑

飞书查询、记录字段回写和应用凭证请求遇到网络超时、连接异常或 HTTP 429/500/502/503/504 ，以及业务码 1254607（多维表数据未就绪）时，最多尝试 3 次，重试间隔为 1、2 秒。单次请求超时为 30 秒。权限、参数等业务错误直接报告；创建类请求不自动重放。日志记录异常类型、尝试次数和恢复结果，不输出凭证或响应正文。

通过运行中服务的队列提交手动重试：

```bash
docker exec design-task-dispatch /app/.venv/bin/python -m app.cli retry <记录ID>
```

本地运行可指定服务地址，使用本地 `.env` 中的 Webhook 凭证：

```bash
.venv/bin/python -m app.cli retry <记录ID> --url https://design-dispatch.kktree.cn
```

命令报告入队状态，最终处理结果查看容器日志和多维表。失败任务可立即重试；正在运行或五分钟内已成功的任务不会重复入队。任务仍经过人工安排保护、创建人部门识别和需求人空白初始化检查。

### 运行日志

默认输出 INFO 摘要，每条正常任务包含开始、需求就绪、识别推荐、任务完成四行。开始行带时间和记录 ID，任务之间以分隔标题和空行区分。补图与异常重试单独记录；最终失败包含失败阶段、总耗时和异常堆栈。已人工安排或结束的任务输出跳过结果。

配置加载、缓存命中、接口读写和匹配依据等细节使用 DEBUG 级别。HTTP 访问日志保留 4xx、5xx，成功请求由业务日志汇总。

在线读取默认最多 10 个资源、3 层内嵌、每份文档 2000 个内容块、每张多维表 100 个字段和 100 条记录；旧 Word 转换限时 60 秒。资源去重，附件和在线图片共用大小与图片限额，超限会标记材料缺口。部署时同步容器外的 `config/materials.json` 和 `prompts/classify.md`。

应用日志同时写入控制台和 `logs/app.log`，单文件上限 10 MiB，保留 5 份备份，UTF-8 编码；任务空行分隔与异常堆栈保留。`LOG_DIR` 指定目录，Compose 将宿主机 `./logs` 挂载到 `/app/logs`。应用日志及 Gunicorn 工作进程错误访问、错误日志进入该文件，Gunicorn 主进程启动日志通过 `docker logs` 查看。

容器使用 UID/GID `10001:10001`。CD 在启动前将日志目录归属设置为该用户，目录权限为 `0750`；当前日志文件为 `0640`。手动部署需先创建宿主机日志目录并执行 `sudo chown -R 10001:10001 logs && sudo chmod 0750 logs`，再启动服务。

主、副负责人共用任务推荐名单。未确认任务按每位系统推荐人各计入完整任务分数；组长确认后，按最终负责人名单计入负载。

## 新增需求通知

程序在匹配、人员推荐和多维表回写成功之后读取最新记录，再通过独立应用机器人发送私聊卡片通知。卡片使用紫色「美工任务上新 · 组长确认」标题，包含任务名称、需求说明、需求人员、所属平台、推荐负责人（主副顺序）及「查看需求」按钮。无法准确匹配或需要人工分配时明确显示待确认结果。回写失败时不发送新增通知；通知失败保留已回写的评级和推荐结果。

通知应用在 `.env` 中配置 `FEISHU_ALERT_APP_ID`、`FEISHU_ALERT_APP_SECRET`，需启用机器人能力和 `im:message:send_as_bot` 权限，接收人须处于应用可用范围。数据读取使用 `FEISHU_DATA_APP_ID`、`FEISHU_DATA_APP_SECRET`。消息接口说明见[飞书发送消息文档](https://open.feishu.cn/document/server-docs/im-v1/message/create)。

`config/notifications.toml` 与字段映射放在同一目录，随现有 config 目录只读挂载，每次通知读取。`new_task.enabled` 控制新增通知总开关；每个 `[[new_task.recipients]]` 包含显示名称 `name`、通知应用下的 Open ID `open_id` 和启用开关 `enabled`。这里填写 `ou_` 开头的 Open ID，须属于 `FEISHU_ALERT_APP_ID` 对应的应用。卡片中的人员引用通过 Union ID 查询通知应用下的 Open ID；通知应用需开通 `contact:contact.base:readonly` 应用身份权限，查询失败时用姓名展示。当前新增通知接收人为软糖、饭团和鸭腿，三人均已启用；配置修改在下一次通知时生效。

发送记录保存在规则缓存目录下的 `notifications/`，Docker 中为持久化卷 `/app/cache/notifications/`，由容器用户写入，消息状态文件权限为 0600。按通知应用、Base、表、记录和接收人去重，成功通知在重跑和容器重建后均跳过。网络瞬时故障最多请求三次，复用同一消息 UUID。发送结果未知且超过飞书一小时去重窗口时停止自动补发，需要核对聊天记录与缓存后处理；缓存损坏时同样停止发送。不要清理通知缓存，否则会失去已发送记录。

仅补发未成功的新增通知（不调用 AI、不修改任务）：

```bash
docker compose exec design-task-dispatch .venv/bin/python -m app.cli notify recXXXXXXXX
```

上线时同步 `config/notifications.toml` 与通知应用环境变量，再重建容器。缺少 TOML 文件或没有启用的接收人时跳过发送。新增需求自动化保留 HTTP 触发步骤，关闭原来的直接发送消息步骤，避免提前或重复通知。最终负责人、组长确认等通知由多维表自动化调用确认通知 HTTP 接口。

## 确认通知 HTTP 接口

多维表自动化以 `POST /webhook/notify` 调用程序，Headers 为 `Content-Type: application/json` 和 `X-Webhook-Token: <与新增需求相同的鉴权值>`，Params 留空。JSON 请求体包含 `record_id`（插入触发记录的记录 ID）和 `event`。

| event | 自动化触发条件 | 接收人 | 卡片 |
|---|---|---|---|
| `leader_confirmed` | 组长确认勾选，最终负责人不为空 | 最终负责人中的所有人 | 美工任务上新 · 已分配：任务名称、需求说明、所属平台、需求人员、最终负责人 |
| `assignee_confirmed` | 负责人确认勾选，最终负责人不为空 | 创建人 | 美工任务 · 负责人已接收确认：任务名称、最终负责人 |

两种通知均为紫色卡片，提供查看需求按钮。TOML 中对应事件的 `enabled` 控制启用；`recipient_field` 引用字段映射键，分别为 `assignee`、`creator`。动态人员 Open ID 通过 Union ID 转换为通知应用下的身份，解析失败时返回 503，不发送给其他人。

接口同步读取最新记录、校验状态并发送，不调用 AI 或修改任务。已取消、已完成或不满足确认条件返回 `skipped`；配置关闭返回 `disabled`；全部成功或已发送返回 `sent_or_duplicate`。业务失败返回 503，可重试相同请求，成功接收人不重复发送。每种事件按记录、最终负责人列表及接收人持久化去重；调整最终负责人后可重新通知，同一负责人组合取消勾选再勾选不会重复通知。调用超时也可重试同一请求。

```json
{"event":"leader_confirmed","record_id":"recXXXXXXXX"}
```

```json
{"event":"assignee_confirmed","record_id":"recXXXXXXXX"}
```
